# CS 305 Software Security – Artemis Financial

This repository contains my Practices for Secure Software Report for Artemis Financial, completed for Project Two in CS 305 at Southern New Hampshire University.

## Reflection

Artemis Financial is a consulting company that builds individualized financial plans for its clients, covering savings, retirement, investments, and insurance. The company has a public-facing web application and wanted to modernize it with current security practices to protect client data. Specifically, they asked for a file verification step in the form of a checksum and for secure communication between the client and the server. That meant finding the existing vulnerabilities in their Spring Boot application, adding a SHA-256 checksum route, and moving the application from HTTP to HTTPS.

I think the thing I did well was combining a careful manual code review with automated scanning rather than relying on either one alone, and tying every finding back to a CWE so it had a standard name and a known fix. The OWASP Dependency-Check scan surfaced 13 vulnerable dependencies, including widely exploited flaws like Spring4Shell (CVE-2022-22965), Ghostcat in the embedded Tomcat server, and remote code execution through SnakeYAML. But the manual review caught problems no scanner would flag: hardcoded "root/root" database credentials, REST endpoints with no authentication, stack traces leaking database details, and a deposit() method that accepted negative amounts and could quietly withdraw money. I then combined both sets of findings into a single mitigation plan ordered by risk, so the most dangerous issues would be fixed first. Coding securely matters because every flaw that ships is an opening someone else gets to choose when to use. For a company like Artemis, which holds sensitive financial information covered by the Gramm-Leach-Bliley Act, a breach means regulatory exposure, cleanup costs, and most of all lost client trust, which is hard to win back. Security built in from the start is far cheaper than security bolted on after an incident.

The most challenging part was working through the dependency-check results. The report on an older Spring Boot release lists hundreds of CVEs, and it takes some care to sort out which ones actually affect the application, which come from transitive dependencies, and which are likely false positives. Getting the tool itself running was its own lesson too: the plugin version in the Project Two starter code depended on NVD data feeds that have since been retired, and the Sonatype OSS Index analyzer now requires its own credentials, so I had to update the configuration before I could get a clean report. That turned out to be helpful, because it showed me that security tooling needs maintenance just like the code it scans.

I increased the layers of security by stacking controls so no single one carries all the weight. The SHA-256 checksum lets a client verify that data arrived unaltered, HTTPS with a self-signed certificate encrypts the connection and protects the checksum itself in transit, and the code fails securely without leaking stack traces to the user. It reminds me a lot of food safety at the farm, where no single check is trusted on its own. In the future I would keep using OWASP Dependency-Check alongside manual review, and I would lean on the OWASP Top 10, the NVD's severity scores, and the vulnerability assessment process flow to decide which issues to fix first and which mitigation fits each one.

To make sure the refactored application was both functional and secure, I wrote JUnit tests that check my hash method against the NIST test vector for SHA-256, confirm the output is 256 bits and consistent, and confirm that changing a single character changes the checksum. I ran the application and verified the checksum in the browser over https://localhost:8443/hash. After refactoring, I reran the dependency-check scan and compared the results. My changes only used Java's built-in MessageDigest class and added no new dependencies, and every finding in the report traced back to libraries that were already in the original code base.

The tools and practices I expect to reuse are OWASP Dependency-Check with an NVD API key kept in my Maven settings.xml instead of the project files, Java keytool for generating keystores and certificates, Spring Boot's SSL configuration, and the habit of using vetted standard libraries instead of writing my own cryptography. Writing unit tests against known test vectors is another practice I will carry forward, since it gives a quick way to prove that security code does exactly what it claims to do.

For future employers, I would show this report along with the refactored code as an example of taking an existing application, assessing it, and improving its security end to end. It shows that I can run and interpret a vulnerability scan, choose and justify a cryptographic algorithm, implement it correctly in Java, configure HTTPS, and document the whole process clearly for a client. That combination of hands-on fixing and clear explanation is a big part of what secure development work actually looks like.
